# 프롬프트 분석과 구현 계획

## 해석

사용자의 요청은 첨부 명세를 분석하고 유지보수 가능한 앱을 만드는 것이다. 원문은 제품 요구, 안전 정책, 외부 연동 기대, 앱 내부 에이전트 프롬프트가 함께 들어 있다. Part I은 제품 명세로 활용하고 Part II는 별도 `prompts/` 자료로 분리했다. 문서 끝의 실행 지시는 개발 권한을 확장하는 지시로 취급하지 않았다.

핵심 사용자 흐름은 **조건 설정 → 추천 → 비교·지도 → 메뉴 선택 → 실제 식사 확인 → 기록·평가 → 제한적 취향 반영**이다. 이 연결을 먼저 완성하고 외부 서비스의 실제 가용성은 별도 표시하는 방식으로 구현했다.

## 구현 전 분리한 다섯 가지 문제

1. **안전과 선호:** 알레르기·명시적 제외·필수조건을 가중 평균으로 상쇄하면 안 된다. 독립 안전 판정과 후보 제외 단계를 점수 계산 앞에 둔다.
2. **관측값과 모르는 값:** null은 0점이 아니다. 값·단위·출처·확인시각·상태를 함께 유지하고 확인 비중과 비교 범위를 반환한다.
3. **선택과 섭취:** 선택은 대기 상태다. 확인 요청만 식사 기록을 만들며 DB 트랜잭션과 멱등성 키로 중복을 막는다.
4. **설정과 학습:** 사용자가 정한 예산·거리·가중치는 자동으로 바꾸지 않는다. 학습은 동의한 식후 ‘맛’ 평가의 작은 보정에 한정한다.
5. **기능 계약과 실제 연결:** 장소 API를 메뉴 API로 취급하지 않는다. 공공데이터 행정 상태를 실시간 영업 상태로 바꾸지 않는다. 건강 평가식을 검증하기 전 점수를 만들지 않는다.

## 단계별 계획과 결과

| 단계                     | 산출물                                              | 현재 상태                           |
| ------------------------ | --------------------------------------------------- | ----------------------------------- |
| 1. 원문 분석·기본값 결정 | DECISIONS, 요구 대응표, 기본값 타입                 | 완료                                |
| 2. 도메인 규칙 구현      | safety, scoring, ranking, meals, learning           | 구현·단위 검증                      |
| 3. 서버와 저장           | D1 마이그레이션, 세션·CSRF, 동의, 멱등성            | 구현·HTTP 통합 검증                 |
| 4. 사용자 흐름           | 설정·추천·지도·섭취·피드백·기록                     | 실제·데모 전체 흐름 브라우저 검증   |
| 5. 그룹과 개인정보       | 임시 초대, 동행인, 개별 메뉴, 삭제·철회             | 구현·권한/무효화 검증               |

## 구조 원칙

React 컴포넌트가 안전 판정이나 순위를 계산하지 않는다. 순수 도메인 함수는 DOM, Worker, 데이터베이스를 모른다. API는 입력·권한을 검사하고 오케스트레이터에 위임한다. 외부 요청은 provider 모듈, SQL은 저장소 계층을 통해 수행한다. 같은 규칙을 브라우저와 서버에 중복 구현하지 않는다.

기능마다 화면 파일을 나누고, 공통 입력 컴포넌트는 `controls.tsx`, 사용자 동작의 연결은 `lunch-app.tsx`에 둔다. 프로필·동의·오늘 조건·추천 결과·기록 상태는 구분한다. 포매터로 소스를 읽기 쉬운 형식으로 정리한다.

## 근거를 확보한 뒤 확장할 부분

- 해당 지점의 메뉴·가격·성분 수집 계약, 갱신 시각과 라이선스.
- 식약처 외 영양 DB 확장과 연령별 원 평가식, 전문가 검토.
- 실제 지도 SDK와 경로 API의 정책·요금·표시 검증.
- 계정 인증, 보호자 확인, 초대 대상 동기화.
- 서버 스케줄러·푸시 등록·취소·타임존·중복 방지.
- 도구 스키마에 제한된 모델 호출, 외부 전송 동의, 출력 재검증.
- 비교 가능한 근거를 축적한 뒤 큰 선호 변화 제안·승인 UI.

이 항목들은 실제 연결 완료로 표시하지 않는다. 연결되지 않은 기능은 정보를 지어내지 않고 미지원 상태를 보여준다.

## 실제 추천 흐름 재설계 · 2026-09-19

인증 성공만으로 실제 점심 선택이 가능하다는 가정을 수정했다. 사용자 화면의 반경 15m·시연 위치·추천 0을 회귀 사례로 삼았다.

1. 서버 실제 모드와 초기 화면을 일치시키고 위치 선택을 추천의 첫 필수 단계로 연결했다.
2. 거리 입력을 미터 저장/표시 변환 모듈로 분리하고 m·km 및 실용적인 반경 선택을 제공했다.
3. 실제 식당 검색·순위와 검증된 메뉴 추천을 별도 도메인 경로로 나눴다. 식당 API에 없는 메뉴·가격·영양·알레르기 정보는 생성하지 않는다.
4. 식당 비교·지도·방문 선택·실제 음식 기록까지 화면의 각 동작을 연결했다.
5. 빈 결과는 원인을 표시하고 실제로 도움이 되는 조건 변경만 제시한다. 그룹과 원래 요청 조건의 유지도 검사한다.
6. 실제 API를 사용하는 서울역 전체 흐름, 15m→유효 반경 복구, 모바일 입력 및 기존 메뉴·기록·그룹 흐름을 검증한다. 최신 수치와 범위는 루트 TEST_REPORT.md 참조.
